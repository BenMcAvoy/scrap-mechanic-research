# Scrap Mechanic DLL development instructions

These instructions apply when the agent is started in `C:\Users\Ben\scrap_research`.

## Workspace layout

- DLL projects live under `./projects/`.
- The Scrap Mechanic MCP server is `./scrap-mechanic-mcp/`.
- Native game logs are under `./Logs/` and project-specific logs may be under `%TEMP%`.
- Crash reports and debugger artifacts are written under `./reports/scrap-mechanic/` unless `SCRAP_MECHANIC_MCP_REPORTS` is set.
- Preserve unrelated binaries, IDA databases, logs, archives, and untracked research artifacts.
- Never use destructive repository-wide cleanup commands.

## Skills and code discovery

- For every Scrap Mechanic task, always use the `$scrap-mechanic-research` plugin and its relevant `scrap-mechanic-research:*` skill. Do not treat the autonomous DLL workflow as the default for every task: ordinary reverse engineering, IDA investigation, documentation, and code review should follow the user’s requested scope.
- Select the narrowest skill that matches the task: manager, global, Lua function, Lua bridge, event, networking, script loading, serialization, or game-message investigation.
- Prefer Codebase Knowledge Graph MCP discovery in this order: `search_graph`, `trace_path`, `get_code_snippet`, `query_graph`, then `get_architecture`.
- Fall back to `rg` for string literals, logs, configuration, build files, and non-code files.
- Do not guess Scrap Mechanic addresses, offsets, vtable slots, or function identities. Validate them against the current binary and corroborating references.

## IDA database annotation

Annotation is a continuous investigation goal, not an optional cleanup step. Whenever IDA reveals a new function, argument role, field, call path, or clarifies what an existing function does, immediately preserve that understanding in the IDB whenever the evidence supports it:

- Rename the function from its autogenerated name to an evidence-based descriptive name whenever confidence is sufficient.
- Rename function arguments from generic names such as `a1`, `a2`, or `a3` whenever their role can be established or strongly inferred.
- Apply useful argument, return, structure, and pointer types when supported by evidence.
- Add concise comments to important call sites, fields, branches, and unresolved assumptions.
- Preserve original names, addresses, evidence, confidence, and version-specific assumptions in the final report.
- Do not leave newly understood functions or arguments under generic names merely because the investigation is still in progress. Use a provisional but evidence-based name and refine it as understanding improves.
- At the end of each investigation pass, review the touched functions and ensure the IDB reflects the current understanding before reporting completion.
- Freely apply and save IDB metadata changes, including renames, argument names, types, comments, bookmarks, enums, structures, and database annotations, without asking for confirmation.
- The only IDA confirmation gate is modifying executable bytes or patching instructions/data bytes. Ask immediately before that byte write and do not infer permission from general modding or analysis instructions.

## Autonomous DLL workflow (explicit opt-in)

Activate this loop only when the user explicitly asks for autonomous DLL work, such as “get the DLL working autonomously,” “self-test until it stops crashing,” or equivalent. For normal reverse engineering or implementation requests, complete the requested investigation/change without inventing an autonomous test loop.

When activated, perform the full loop rather than stopping after compilation:

1. Inspect the target project, its README, build configuration, existing logs, and relevant skills.
2. Establish explicit success criteria and a finite iteration limit. If the task does not provide one, use 8 iterations and ask only if success cannot be made observable.
3. Build with the project’s existing build system. For xmake projects, inspect the project’s `xmake.lua` and use its configured target; do not invent a new build path.
4. Verify the produced DLL path, timestamp, architecture, and any required exported cleanup function.
5. Launch Scrap Mechanic through the MCP when it is not already running. Prefer the null-driver launch unless rendering is required.
6. Inject the verified DLL with the MCP using an absolute path and the current game PID.
7. Record the latest event ID, then use `wait_for_event` with `after_id` and a suitable timeout. Prefer this blocking tool over client-side polling; unsolicited MCP notifications may not wake the Codex harness.
8. Test the requested behavior in the game and inspect the relevant DLL/game logs.
9. On `process_crash`, `debug_exception`, `debug_dump_ready`, or `crash_report_ready`, call `get_run_report` and `get_debug_events`, then inspect all referenced artifacts before editing code.
10. Make one focused change, rebuild, and repeat. Keep a short iteration record containing the hypothesis, change, result, and next action.
11. Use `uninject` only when the DLL has a known cleanup export. Otherwise stop/restart the game before reinjecting; never force-unload a DLL that may still have active hooks or threads.
12. Stop when the success criteria are demonstrated, the iteration limit is reached, or repeated infrastructure failures prevent meaningful progress.

## MCP runtime tools

- `game_status`: identify the running game and lifecycle state.
- `launch_game`: start the game; use `keep_graphics=true` only when necessary.
- `inject`: load an x64 DLL into the game.
- `uninject`: cleanly unload a DLL through its cleanup export.
- `wait_for_event`: block for lifecycle/debugger events; pass `after_id` to avoid matching stale events.
- `get_run_report`: locate crash reports and diagnostic artifacts.
- `get_debug_events`: inspect lifecycle, exception, dump, and breakpoint events.
- `read_memory`/`write_memory`: inspect or change live process memory when the task requires it.
- `set_hardware_breakpoint`/`clear_hardware_breakpoint`: use hardware breakpoints for targeted runtime investigation.
- `stop_game`: terminate the selected game process when a clean restart is required.

The MCP currently has no approval gate for injection, unloading, or memory writes. Still validate paths, PIDs, addresses, module bases, and cleanup behavior before acting.

## Failure handling

Treat these as distinct outcomes:

- build failure;
- missing or wrong-architecture DLL;
- injection or unload failure;
- debugger supervisor attach failure;
- timeout;
- normal process exit;
- game crash with exception data;
- game crash detected only through process exit or external crash-report artifacts.

If no exception event is available, use the exit code, report directory, BugSplat artifacts, game logs, DLL logs, and the last successful iteration as evidence. Do not claim a root cause without supporting evidence.

## Completion report

At the end of an autonomous run, report:

- final DLL path and build target;
- success criteria and whether they were demonstrated;
- iteration count;
- key code changes;
- crash/error evidence and artifact paths;
- remaining limitations or unverified behavior.
